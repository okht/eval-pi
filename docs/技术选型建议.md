# EvalPi 技术选型建议

日期：2026-09-23｜状态：基于官方文档的候选方案，尚未安装或运行集成验证。

用户已确认桌面应用作为主要入口，并提出使用 pi.dev。当前推荐组合为 Electron + React + TypeScript + Pi SDK，搭配独立的评测执行层与本地持久化。

## 推荐职责划分

| 部分 | 候选技术 | 负责内容 |
| --- | --- | --- |
| 桌面应用与界面 | Electron、React、TypeScript | 聊天、侧栏材料、文件夹选择、进度、批量复核和桌面生命周期。 |
| Agent 后台 | 独立 Node.js 进程中的 Pi SDK | 理解项目与目标、调用工具、组织分析、修改项目副本、向界面推送执行事件。 |
| 模型调用 | Pi 的模型接入层；需要独立调用时使用 pi-ai | 按配置调用主模型和打分模型；具体供应商和端点仍需兼容性验证。 |
| 评测执行 | EvalPi 自有 TypeScript 任务执行层 | 执行已确认的计划、调度 Case、记录重复次数、重置状态、组织打分、执行预算和停止规则。 |
| 项目状态与材料 | SQLite 与本地文件 | 保存标准、数据集、版本、判定、运行状态及结果；大日志与报告按文件保存。 |
| CLI | 复用应用的业务服务与任务协议 | 让其他 AI 助手操作同一套项目和评测能力。 |

这是职责划分建议，不要求每一项都建立独立服务。

## Pi 能提供的基础

官方 SDK 包名为 `@earendil-works/pi-coding-agent`，可以嵌入 Node.js 或 Bun，提供会话、工具、模型、资源加载和执行事件。其会话与流式事件适合接入桌面聊天与进度界面。[Pi SDK](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/sdk.md)

自定义工具可以承载生成评测计划、启动评测、获取结果、请求复核等业务操作；事件可以连接界面和运行记录。Pi 的扩展文档为工具、事件和状态提供了接口，但 EvalPi 的业务流程仍需实现。[Pi 扩展](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/extensions.md)

`@earendil-works/pi-ai` 提供多供应商模型调用。被测 Workflow 的业务 API 则需要另行接入，模型供应商适配不能自动解决业务系统的输入、会话和状态复原。[pi-ai](https://raw.githubusercontent.com/earendil-works/pi/main/packages/ai/README.md)

## 为什么推荐 Electron

Electron 的主进程和 utility process 支持 Node.js。推荐在独立后台进程中承载 Pi，由界面通过消息接口访问，避免把长时间任务放进界面进程。后台可以作为 SDK 的宿主；若采用 Pi 子进程通信，官方也提供 RPC 接口。[Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)、[Pi RPC](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/rpc.md)

Tauri 也可承载这个产品，但运行 Pi 时需要额外包装 Node sidecar 或附带相应运行时，并管理其打包、通信和生命周期。对于已经选择 Node/TypeScript Agent SDK 的路线，Electron 的组合更直接；这是工程判断，尚无本项目的体积或性能实测。[Tauri Node sidecar](https://v2.tauri.app/learn/sidecar-nodejs/)

## 需要 EvalPi 落实的核心能力

1. **可靠的评测流程。** 标准生成与版本管理、样本合成和校验、重复运行、打分器校准、批量复核、回归与盲测，均需要产品自己的业务逻辑。Agent 提出和调用操作，执行层校验已确认的条件。
2. **评测隔离。** 独立会话负责隔离上下文；项目副本、业务状态复原与文件访问边界负责其他隔离。盲测题目与答案需要由独立评测过程持有，限制优化执行方的实际访问。Pi 默认继承宿主进程权限，隔离措施需要另行设计。[Pi 权限说明](https://raw.githubusercontent.com/earendil-works/pi/main/README.md)
3. **可恢复的任务与一致配置。** 已确认的标准、授权、计划和执行记录需要独立持久化，聊天记录用于沟通与追溯。应用崩溃、任务取消或重启后的恢复规则，以及对话、侧栏和 CLI 如何读取同一份有效配置，需要明确实现。

被评测项目可以继续使用自身的语言和框架；EvalPi 通过运行入口或 API 调用它，并收集必要的运行证据。接入能力的范围需要用真实项目验证。

## 技术定案前的验证项

这些验证用于判断底层技术可行性，不改变已确认的最终产品范围。

- 用桌面界面启动 Pi 后台会话，验证流式输出、工具事件、取消和后台退出处理。
- 在项目副本中完成一次实际的检查、修改、运行与版本比较。
- 验证同一 Case 的重复执行及状态复原，并验证优化执行方无法访问隔离的盲测材料。
- 用实际需要的模型 API 验证主模型与打分调用，核对用量信息与失败处理。
- 将方案与结果持久化，验证重启后能够识别完成、失败、等待复核和未完成的工作。

本项目在 Windows 上开发和验证时，命令执行必须遵守项目约定：显式使用 PowerShell 7，缺失时停止，不回退到 Windows PowerShell。Pi 的可选 PowerShell 工具存在回退行为，因此接入时需要选择能够落实该约定的工具配置或自定义执行工具。[Pi Windows 文档](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/windows.md)
