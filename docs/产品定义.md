# EvalPi 产品定义

状态：讨论收敛稿｜更新日期：2026-09-23

本文整理当前对话已经确认的最终产品形态，不限定第一版范围，也不代表已开始开发。末尾单列待确定的问题。所有示例场景和数字均用于解释，不代表真实项目数据或已确定的验收阈值。

## 1. 产品定位与核心价值

EvalPi 是面向 AI 产品经理的、以评测驱动持续调优的独立桌面应用，并提供供其他 AI 助手操作的 CLI。

用户通过自然语言交付项目、说明目标，Agent 自动理解项目、建立评测、发现问题、修改实现并反复验证，交付改进版本、效果对比和剩余问题。

核心场景：用户已经初步搭好一个 Agent 或 Workflow，希望把它从效果不足的状态，持续调优到用户认可的可用水平。

「从 50 分到 80、90 分」是价值的直观表达。实际成功条件由具体业务要求、产品运行成本和响应时间等约束共同定义；不能承诺任意项目必然达到某个分数。

单独评测也可以使用。完整主线是：

> 交付项目与目标 → 理解项目、补齐关键信息 → 用户确认方案 → 建立基线 → 评测、归因、修改、复测 → 回归与独立盲测验证 → 用户验收改进版本。

## 2. 用户、对象与输入

主要服务 AI 产品经理。项目作为组织容器，可以包含一个或多个待评测对象；评测对象可以是完整 Agent、Workflow、单项业务能力，或带有业务提示词的模型。

| 输入 | 已确认的产品行为 |
| --- | --- |
| 本地项目文件夹、路径或可访问的项目地址 | 用户在对话中交付；Agent 自行检查可发现的结构、入口、依赖和运行方式，尽量完成接入准备。 |
| PRD | 支持飞书云文档与 Markdown；PRD 为可选材料。 |
| 目标描述、评测标准、已有数据集 | 支持用户直接提供，也支持 Agent 根据项目和对话提出草案。 |
| 已有问答、运行记录、日志或模型输出 | 支持基于现有材料开展评测，并明确现有证据可以支持的结论。 |

没有 PRD、明确指标或现成测试集，也应该能够开始。Agent 先理解现有项目，再追问无法从材料中可靠确定的业务目标和标准。

需要区分「项目当前如何运行」与「业务要求它如何运行」。实现代码可以帮助理解项目，不能自动成为正确业务规则。

输入与权限决定本次能做到的深度：仅有输出记录时，可以分析输出质量；新一轮执行、后台状态核验和实际修改，需要相应入口、证据和权限。缺少条件时应说明能够完成的工作与缺口。

## 3. 交互形态

以桌面应用作为主要入口。所有评测配置与决策以自然语言对话完成，包括评测目标、规则、数据集、模型角色、API、打分标准、复核方式和调优范围。

- 对话展示简短解释、关键进度、需要用户决定的事项，以及详细材料的索引。
- 侧栏展示已确认的信息和详细材料，包括项目理解、评测方案、标准、数据集、打分器、结果、修改记录和报告。
- 支持类似对话助手的上下文确认窗口，尤其是批量 Badcase 复核。
- 用户可以用自然语言修改配置，不需要先完成一套复杂表单。
- CLI 为其他 AI 助手提供操作入口；具体命令协议尚未确定。

「自然语言配置」保留侧栏和必要的辅助控件。不能将需求解释成所有内容都必须堆在聊天消息里，或完全取消可视化详情。

## 4. 模型与打分器

支持配置多个模型或 Agent 的 API，并根据任务分配角色：

| 角色 | 主要职责 |
| --- | --- |
| 待评测对象使用的模型 | 执行业务任务；可以分布在 Workflow 的不同节点。 |
| LLM 打分器 | 按已确认标准评价语义、业务质量等内容。 |
| 主模型 | 理解项目与需求、组织评测、生成评测与打分提示词、检查打分器、归因和组织调优。 |

这些角色可以复用模型，不要求每个角色独立采购或部署。

用户表达业务要求和评测标准，Agent 负责转成可执行的评测规则与提示词。也允许用户提供已有提示词。

以 LLM-as-a-Judge 为主要能力，结合适合任务的程序检查和实际状态核验。例如，判断售后申请是否提交成功，需要对应工具结果或后台状态证据。

支持评测和校准打分器：保留人工判定样本，用主模型检查误判、提出打分提示词调整，并在另一批样本上验证。主模型更强并不自动意味着其判定正确；证据不足时允许无法判断。

## 5. 方案确认与目标约束

Agent 可以先检查项目并开展必要的探索性准备；正式评测在用户确认方案后开始。

方案需要让用户理解本次：

- 评什么、希望改善什么、以什么标准验收。
- 使用哪些材料与数据集，关键预期结果有什么依据。
- 使用哪些模型与打分器，怎样执行、重复和验证。
- 哪些信息已具备，哪些证据或接入条件仍然缺失。
- 是否只评测，或同时调优；允许修改到什么程度。
- 是否人工复核 Badcase，以及本次预算与停止条件。

确认时展示少量有代表性的正常、明显失败和边界案例及其预期判定；详细标准和完整数据集通过侧栏查看。

明确区分两组限制：

1. **调优后产品的运行要求**：业务效果、单次任务成本、响应时间等。Agent 在用户确认的限制内提高效果。
2. **本次评测与调优的资源预算**：费用、时间、执行次数或迭代上限。

Agent 可以提出具体数值供确认，当前没有任何统一默认数值已经确定。无法同时满足要求时，展示改善与差距，提出调整建议，经用户决定后再改变限制。

## 6. 数据集与独立验证

| 数据集 | 用途 |
| --- | --- |
| 迭代集 | 为定位问题、修改实现和检查修复提供可见样本。 |
| 回归集 | 检查调整后原本具备的能力是否退步。 |
| 盲测集 | 在候选版本固定后，检查其在未用于指导修改的样本上的表现。 |

Agent 根据业务标准、真实样本和 Badcase 提取能力要求与失败模式，自动合成测试样本，其中包括独立的盲测集。

合成应覆盖正常、边界和异常情形，改变有意义的条件、信息组合或对话路径，并检查业务依据、预期结果、有效性和重复情况。合成内容不能仅凭生成模型的判断就获得正确答案的地位；具体自动检查方法仍需设计。

盲测规则：

- 优化执行方不能读取盲测题目与预期答案；盲测由独立评测过程执行。
- 用户可以查看侧栏详情；提供给优化执行方的上下文和文件访问必须保持相应隔离。
- 同轮原版本与候选版本使用同一批冻结的盲测样本和一致的比较条件。
- 重复执行同一轮盲测时，不能通过更换题目掩盖不稳定表现。
- 某个盲测样本被用于指导修改后，转入可见的迭代材料，后续独立验证需要补充新的盲测样本。

同一轮比较固定评测标准、数据集和打分器版本。需要调整标准时，由用户确认，并让原版本与候选版本在调整后的条件下重新比较，保留历史结果。

## 7. 重复运行与状态隔离

支持同一评测集或 Case 多次执行，以观察随机性与稳定性。

- 用户指定准确次数时按指定次数执行。
- 用户指定范围、费用或时间上限时，Agent 在范围内选择执行次数。
- 未指定时，Agent 根据任务特征、稳定性和成本提出安排，纳入方案。
- 区分独立 Case 数与实际执行次数，例如 100 个 Case 各运行 3 次，对应 300 次执行。

每个 Case 的每次尝试，从该 Case 预设的初始状态开始：

- 不继承上一个 Case 的对话、任务记忆或临时产物。
- 同一 Case 内的多轮对话保留必要上下文。
- 复原会影响行为的外部业务状态、临时文件和缓存条件。
- 固定的只读知识、规则与配置可以保持不变；响应时间比较需要明确相关缓存条件。
- 无法控制的外部状态应在结果中说明，并限制对应结论。

组织评测的 Agent 保留计划、进度与结果；被测对象和逐 Case 打分上下文按测试要求隔离。

展示逐 Case 的通过次数与失败情况。偶发失败也形成候选 Badcase，再核查属于目标系统、打分器、环境或测试设计的问题。

## 8. Badcase 批量复核

人工确认可以选择开启或关闭。开启时，按批次提供复核窗口，支持多选和批量提交，不逐条弹窗打断。

候选问题可以按类型分组，展示摘要、影响、案例与证据索引；每个 Case 保留独立证据和判定。

| 用户在批次中的处理 | 提交后的行为 |
| --- | --- |
| 确认有问题 | 记录人工确认，进入本次授权范围内的报告或调优流程。 |
| 判定无问题 | 保留人工判定，移出当前待处理问题列表。 |
| 不确定，再核查 | Agent 按标准和证据继续核查。 |
| 未选择 | 批次提交后，同样交给 Agent 核查。 |

自动核查结果：确认有问题则进入 Badcase 流程；确认无问题则移出当前问题列表；仍证据不足则保持待定、记录缺失证据，并继续处理其他问题。

明确的人工判定予以保留。待定项暂不进入自动修复；后续获得新证据时可以重新核查，避免无休止重试或重复打断。

人工复核也包含少量系统判定通过的样本，用于发现漏判，可结合随机抽样、边界样本和高影响情形。Agent 推荐抽样安排，用户可以调整。

人工判断与纠正保留为项目校准材料，注明来源与依据。Agent 自行复核的结果保留其自动判定来源。

## 9. 自动调优与授权

当用户要求改善项目并确认修改范围后，Agent 在独立副本中连续完成：

> 核查失败 → 查看运行记录和证据 → 提出归因并验证 → 修改实现 → 复测与回归 → 独立盲测 → 判断是否继续。

权限可以覆盖内部结构调整，包括更换模型、拆分或合并节点、增加校验步骤，以及修改相关代码。无需把它限定为提示词和参数优化。

自主修改须遵守已经确认的业务规则、对外接口约定、产品运行限制和本次预算。需要突破授权范围时，应提供具体调整方案，由用户确认。

保留原始基线、修改记录与比较结果。项目副本与外部业务环境分别处理；复制代码不能直接证明外部账号、数据库或服务状态已隔离。

停止条件纳入方案：

- 达到约定目标，并完成对应回归和独立验证。
- 达到费用、时间或迭代上限。
- 连续尝试未带来有意义的改善。

未达标时，交付当前最佳候选版本、已验证的改善和剩余差距。最终是否采用或合入原项目，由用户决定。

## 10. 交付与呈现

报告面向 AI 产品经理和研发共同使用。默认交付 PDF 与应用内预览；通过对话中的文件索引链接查看或保存，生成和导出由自然语言请求发起，不设置独立的导出配置页面或专门的导出按钮。

报告内容、结构、章节、标题、顺序和页数由模型根据实际评测材料自主决定。结论、效果与代价对比、关键改动、代表 Badcase、剩余问题和结论范围等信息按需组织；完整逐条结果与 Trace 可通过附录文件链接提供。报告保留生成时的评测版本与人工判断，后续迭代不覆盖历史报告。

报告视觉采用简洁研究报告风格，并由 `eval-pi-design-system` 统一维护。应用和报告参考 pi.dev 的实际视觉体系：暖灰纸面、深蓝灰文字、蓝色数据与少量陶土色强调，配合细网格和清晰细线。英文采用 Plantin、Departure Mono、Commit Mono，中文搭配 Noto Serif SC；应用内预览与 PDF 共享字体角色和配色，并按媒介适配排版。设计系统仅固定视觉规范，组件按需组合；示例中的 90% 目标、4 个指标、3 页布局及全部数值不约束实际报告。已有证据与待定内容保持清晰区分。当前优先完成报告视觉，后续再统一应用工作区。

应用通过 `scripts/sync-report-design.mjs` 从本地设计系统检出目录同步主题、样式、字体和 Logo，主题与样式保存在 `src/design-system/reports/`。浏览器读取应用携带的资源，无需私有仓库凭据。字体来源与许可随资源保留；当前中文字体为示例子集，生成任意中文报告时需依据最终正文动态生成子集，或采用覆盖充分的完整字体。

评测任务交付：结果摘要、候选或已确认的 Badcase、对应证据、归因或待验证假设、改进建议和证据缺口。

调优任务额外交付：可交付的候选版本、修改内容、原版本与候选版本的比较、回归与盲测结果、产品运行成本和响应时间变化，以及未解决的问题。

用户在对话中看到关键结论和进度，在侧栏查看完整材料。结论应能够追溯到相应版本、标准、样本和执行证据。

## 11. 用于走查的示例场景

已选择「电商售后客服 Agent」作为讨论样例，并关注「声称已经提交售后申请，实际没有提交」的问题。

示例验证需要结合测试后台、订单状态或工具结果，判断实际业务动作与对用户的回复是否一致。拿不到对应证据时，只能报告能够验证的部分。

这是说明产品流程的例子，不代表 EvalPi 的服务范围只限客服，也不代表已经检查过真实客服项目。

## 12. 待确定的问题

以下内容尚未形成确定需求，不应直接写成开发承诺：

| 问题 | 为什么影响产品定义 |
| --- | --- |
| 执行环境与平台范围 | 桌面应用作为主要入口已确定；支持的操作系统，以及本地、企业环境、云端的执行边界仍需明确。 |
| 接入与真实业务验证条件 | 自动发现和准备接入已确定；缺少依赖、权限、测试账号或隔离环境时的降级交付与协作流程仍需具体化。 |
| 标准与合成样本的依据管理 | 需要区分用户确认、业务文档、实现推断和 Agent 建议；有效性检查、争议处理及进入正式验收的门槛仍需定义。 |
| 对话、侧栏与 CLI 的配置一致性 | 需要明确修改如何反映到持久化材料、运行中变更何时生效，以及版本、撤销和并行任务如何处理。 |
| 真实用户价值验证 | 当前定位来自需求讨论；仍需真实使用样例验证，用户能否更少配置、更少复核，并获得有证据的实际改善。 |

这些问题用于继续收敛最终形态。开发顺序、具体技术方案、商业模式与数值默认值，均尚未在本轮确定。用户提出 Pi 作为 Agent 框架候选，官方文档核查与技术组合建议见 [技术选型建议](技术选型建议.md)。
